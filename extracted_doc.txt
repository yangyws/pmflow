第一章、功能說明
1.1 功能定位 
遠距投保（Remote Insurance）為多媒體遠距銷售平台之核心功能，提供招攬員與客戶（要保人 / 被保人 / 法定代理人）在視訊會議環境中，完成要保書簽署、同意書確認、健康告知事項核對，以及招攬員簽名等全程合規線上投保作業。
本功能由外部系統 ePOS（eAppForm）發起，透過 registerMeetingRoom API 申請會議室後，由本平台主持整個投保流程，最終將簽署結果透過 doRmSignSuccess / doRmSignFailed 回送 ePOS。
遠距投保 主要整合以下資訊與功能：
招攬會議室
網投會員登入
網投會員重設密碼
MID認證
桌面分享
寄送簡訊
寄送電子信箱
投保招攬員畫面錄影
顯示招攬員登錄證
審閱三份同意書
人臉註冊
身分證驗證
要保文件審閱
要保人確認告知事項
要保文件簽署
投保內容確認聲明
高齡錄音

第二章、作業流程
流程一：申請遠距投保會議室
流程圖
流程說明
ePOS eAppForm 發起遠距投保申請，呼叫 POST /registerMeetingRoom，帶入 caseNo、flowType、targetType、agyCode、sourceType、eappGuid 等參數。
VFA 後端接收請求，驗證 Token 與參數合法性。
驗證失敗（token 解讀錯誤 400、逾期 401、未提供 403、其它錯誤 300）→ 回傳對應錯誤碼，ePOS 端顯示錯誤、不開啟會議室。
驗證成功後，VFA 後端建立會議室 Session 並準備資料寫入。
VFA DB / 會議室服務寫入會議室記錄，產生唯一 roomIdePOS 收到 roomId 後，另開新視窗 redirect 招攬員（帶 token + roomId）。
VFA 後端回傳結果 { code: "100", roomId } 給 ePOS。
ePOS 收到 roomId 後，另開新視窗，將招攬員瀏覽器導向會議室頁面（?token=&roomId=），進入流程二。
角色情境說明（由 flowType + targetType 決定）
argetType：1 = 要保人端、2 = 被保人端、3 = 要被保人不同人（要保人端與被保人端分開申請各自的會議室）。
要被保「同一人」（flowType 01~03）：一次申請會議室即可。
要被保「不同人」（flowType 04~12）：要保人端、被保人端分開申請會議室。
要保人端先走完整流程後，被保人端需於24 小時內完成自己端的流程。
未成年情境（flowType 0212）：法定代理人參與遠距投保，須與客戶（未成年要/被保人）各自陪同自己的法代入鏡（入鏡規則依步驟而異，非全程同框）。
未滿 7 足歲：所有步驟由法定代理人全程代行（人臉註冊、身分證辨識不得略過，法代與本人各一輪）。
滿 7～未滿 18 歲：每個簽名/聲明步驟，法代先操作、再換本人。
★ 12 種角色情境（flowType 01~12）與法代入鏡規則：
【入鏡規則】有法代時，要/被保人各自與自己的法代同時入鏡（不同要/被保人的法代不互跟）。人臉註冊、身分證辨識、簽署：各別入鏡（法代先，本人後）。確認登錄證、送件前文件再次確認：同框入鏡。
[01] 要被保同人：要/被保人 成年，法代 無。本人自行完成所有步驟，無法代。
[02] 要被保同人：要/被保人 0−6歲，法代 有。法代全代行。人臉+身分證：法代與本人各別入鏡（法代先、本人後）。同框步驟：確認登錄證、送件前文件再次確認。
[03] 要被保同人：要/被保人 7‒19歲，法代 有。人臉+身分證、簽署：法代與本人各別入鏡（法代先、本人後）。同框步驟：確認登錄證、送件前文件再次確認。
[04] 要被保不同人：要保人 成年、被保人 成年，法代 無/無。要保人端先完整流程，被保人端於 24 小時內另訂視訊完成。兩端均無法代。
[05] 要被保不同人：要保人 0−6歲、被保人 成年，法代 有/無。要保人法代先完成人臉+身分證，再換要保人本人（各別入鏡）。同框步驟：確認登錄證、送件前確認。被保人端無法代。
[06] 要被保不同人：要保人 7‒19歲、被保人 成年，法代 有/無。要保人法代先完成人臉+身分證+簽署，再換要保人本人（各別入鏡）。同框步驟：確認登錄證、送件前確認。被保人端無法代。
[07] 要被保不同人：要保人 成年、被保人 0−6歲，法代 無/有。要保人端無法代。被保人法代先完成人臉+身分證，再換被保人本人（各別入鏡）。同框步驟：確認登錄證、送件前確認。
[08] 要被保不同人：要保人 成年、被保人 7‒19歲，法代 無/有。要保人端無法代。被保人法代先完成人臉+身分證+簽署，再換被保人本人（各別入鏡）。同框步驟：確認登錄證、送件前確認。
[09] 要被保不同人：要保人 0−6歲、被保人 0−6歲，法代 有/有。兩端均有法代。要保人端：要保人法代先入鏡，再換要保人本人（各別入鏡）。被保人端：被保人法代先入鏡，再換被保人本人（各別入鏡）。法代各自隨同自己的要/被保人入鏡，不互跟。
[10] 要被保不同人：要保人 7‒19歲、被保人 7‒19歲，法代 有/有。兩端均有法代。要保人端：要保人法代先入鏡，再換要保人本人（各別入鏡）。被保人端：被保人法代先入鏡，再換被保人本人（各別入鏡）。法代各自隨同自己的要/被保人入鏡，不互跟。
[11] 要被保不同人：要保人 0−6歲、被保人 7‒19歲，法代 有/有。兩端均有法代。要保人端：要保人法代先入鏡，再換要保人本人（各別入鏡）。被保人端：被保人法代先入鏡，再換被保人本人（各別入鏡）。法代各自隨同自己的要/被保人入鏡，不互跟。
[12] 要被保不同人：要保人 7‒19歲、被保人 0−6歲，法代 有/有。兩端均有法代。要保人端：要保人法代先入鏡，再換要保人本人（各別入鏡）。被保人端：被保人法代先入鏡，再換被保人本人（各別入鏡）。法代各自隨同自己的要/被保人入鏡，不互跟。
流程二：招攬員會進入會議室/取回要保書資料 (getEappfromData)

§3.5.2.3 客戶 OTP 驗證進入會議室
招攬員進入會議室後，VFA 後端自行產生 6 碼數字 OTP，呼叫保誠 OTP WebService（SOAP）之 sendBySMS(password, systemType, mobile, sms) 發送簡訊，簡訊內容（sms）由 VFA 自帶，含 OTP 碼與客戶端進入連結；同時將 OTP 碼與計時存入 Redis 供後續驗證使用。
招攬員端畫面進入等待狀態，顯示「等待客戶進入」。
客戶點選簡訊連結，開啟客戶端頁面，系統顯示 OTP 驗證輸入畫面。

§3.5.2.3 客戶進入視訊會議室（無需 OTP 驗證）
★ 依主管指示：客戶進入視訊會議室無須輸入 OTP 密碼，移除驗證碼輸入步驟。
後端呼叫保誠 sendBySMS(password, systemType, mobile, sms) 發送含 roomId / token 之進入連結簡訊至客戶手機；客戶點選後直接進入視訊會議室，不顯示 OTP 輸入頁。
後端驗證連結 token 有效性（roomId 有效且未逾時）；驗證通過後建立客戶 Session，記錄進入時間。
後端透過 STOMP WebSocket 推播「客戶已進入」事件至招攬員前端，招攬員端顯示「客戶已上線」並更新視訊格。
客戶端載入 Jitsi 視訊畫面，進入下一步 §3.5.2.4（MID 行動身分識別 / OIB 網投登入，擇一）。
客戶進入會議室後，依 authMethod 進行身分驗證：選擇 MID 者進入流程四，選擇 OIB（網投會員登入）者於客戶端輸入帳號密碼完成登入。MID 或 OIB 任一驗證成功後，VFA 後端透過 STOMP 推播 WS S 事件至 /topic/GetMessage/{roomName}，招攬員端 onSuccess 回呼自動執行 setSearchParams({ step: C })，切換至 §3.5.2.7。

系統呼叫 ID遠距投保/Login，帶入身分證號、手機門號、電信業者代碼及 clausever，取回 Token。
電腦/平板畫面顯示 QRCode，客戶使用手機掃描 QRCode（手機需關閉 WIFI），手機完成 MID 身份驗證後顯示「請回到電腦確認驗證結果」。
       【手機路徑】
客戶點選 SMS / email 連結進入系統，需先關閉 WIFI（否則顯示「偵測到您使用的電信商可能非 XX 電信...」紅色提示）。客戶填寫手機門號並選擇電信業者，系統呼叫 ID遠距投保/Login 取得 Token。
系統呼叫 ID遠距投保/MIDClause 顯示授權條款，客戶閱讀並勾選同意。
客戶填寫手機門號並選擇電信業者，系統呼叫 ID遠距投保/Login 取回 Token。
客戶瀏覽器以 Form POST 方式向 ID遠距投保/DO 發送請求（帶入 Token），在手機上直接完成 MID 身份驗證。
【兩路共同結束】
ID遠距投保 驗證完成後，將 Do Response Form POST 回 VFA 的 ReturnURL。
VFA 後端複查 QueryVerifyResult，判斷 MemberNoMapping：
1 = 一致（成功）→ 取得 inPerson，進入身分證驗證步驟。
2 = 不一致 / MID_FAIL（失敗）→ 後端設 waitingForRecruiter=true，客戶端顯示「請等待業務員提示」（畫面鎖定）；招攬員端業務互動區日誌新增「客戶第 N 次 MID 驗證作業失敗」並出現【重新啟動MID】按鈕。
招攬員點【重新啟動MID】→ 送 RECRUITER_MID_RESTART，後端重置 phase 為 MID_CONSENT、清除 mid、解鎖客戶畫面，客戶重新進行 MID 驗證（目前無失敗次數上限）。

§3.5.2.15.1 客戶要保文件簽署（要保人 / 法定代理人，手機橫放）
接續流程十二，第二段錄影持續進行中，全程偵測人臉，WS 全程常駐；客戶與招攬員雙方簽名完成後，結束第二段錄影。
簽名位置：PDF = getEappformData 的要保書 notifyCode；座標 = signjson.signinfo.xy。
客戶簽名中：客戶端開啟簽名板手寫簽名；同時招攬員畫面鎖定，蓋一層 overlay「要保人 / 法定代理人 簽名中，請稍等」（三個導覽按鈕此時不可按，overlay 文字依當前簽名者動態切換）。
客戶簽完名：招攬員畫面解鎖，先 pop up 顯示剛簽的簽名字跡給招攬員確認，招攬員才可操作三個導覽按鈕：
【重新簽名】→ 客戶端（要保人/法代）重新刷新簽名視窗，重簽（回到步驟 1）。
【下一個簽名】→ 簽名字跡印到 PDF 對應位置（notifyCode 要保書 + signinfo.xy 座標），簽名圖 signimg 寫入 signjson、簽名截圖+時間戳記寫入簽名檔 → 雙方跳到下一個簽名欄位。
【上一個簽名】→ 雙方跳到上一個簽名欄位，招攬員端先 pop up 上一個已印在 PDF 的簽名字跡；招攬員可再按【重新簽名】（客戶重刷）或【下一個簽名】（到下一欄）。
若【下一個簽名】那欄剛剛已簽過（例：簽名→上一個→下一個）→ 招攬員端也會跳出該欄已印在 PDF 的簽名字跡。
簽名比例不符合 → 系統要求按正常比例重簽（為日後要保書套印清晰度）。
客戶所有簽名欄位完成 → 最後一欄按鈕轉為【確認儲存】→ 進入招攬員簽署。
§3.5.2.15.2 招攬員要保文件簽署（被保險人流程則省略此段）
招攬員簽署自己的欄位；客戶端顯示「招攬人員簽署中，請稍候」並持續偵測人臉。招攬員簽名導覽與客戶不同（無 pop up 預覽）：
【下一個簽名】→ 招攬員簽名直接印到 PDF 對應位置。
【重新簽名】→ 清空該 PDF 位置（重簽）。
招攬員完成所有簽名欄位 → 第二段錄影結束。後端非同步上傳第二段影片（Redis stage = step2），流程立即繼續進入 §3.5.2.16；失敗則 WS 推播 RECORDING_FAILED（failedStage:"step2"），雙方重新進入從 step2 重錄。
eKYC 簽名身分驗證（工研院 FRS 子系統）
每個簽名欄位完成後，VFA2.0 即時呼叫 POST /ekyc/face/verify，送入當前入鏡截圖確認「簽名者是否為應簽名本人或法代」，防止他人代簽。
Request：{ uuid（案件唯一識別碼）, liveFaceImage: Base64（截圖） }　Response：{ match: bool, score: float }
未滿 7 足歲（同框代簽—紅框「大人抱小孩」）：系統將畫面上下分割截圖，各送一次 eKYC API——上半框 → verify(法代 uuid)、下半框 → verify(要/被保人 uuid)；每欄共呼叫兩次。
滿 7～未滿 18 歲（分批入鏡）：法代簽署時 snapshot → verify(法代 uuid)；換本人入鏡簽署時 snapshot → verify(本人 uuid)；每欄共呼叫兩次。
match=false 時：系統記錄警示通知招攬員；實際阻擋與重驗規則待 BU 確認後補充。
eKYC 子系統實作由工研院負責（API endpoint、Face Matching、DEK/KEK 加密儲存）；VFA2.0 僅負責截圖、呼叫 API、保存 UUID、顯示 match/score 結果。

§3.5.2.16 投保內容確認聲明（第三段錄影）
主控權與頁面驅動
此階段主控權在招攬員端：客戶端逐字反紅速度、翻頁、進入下一段聲明，全由招攬員操作驅動；客戶端無法自行操作，僅被動跟讀。

全程人臉身分驗證（eKYC Face Verify API）
聲明錄製期間，系統全程持續呼叫 POST /ekyc/face/verify 確認入鏡者身分。

Backend Business Logic

第五章、資料庫處理邏輯
說明：遠距投保（meet-serivce）目前持久化策略以 Redis + in-memory 為主，無遠距投保專屬關聯式資料表；僅共用平台層稽核表。以下分「現況」與「未來預計設計」。
5.1 現況：無遠距投保專屬資料表
meet-serivce 雖啟用 JPA（@EntityScan com.pcalife.msp.common.entity、@EnableJpaRepositories），但服務本身設定檔未配置 datasource；遠距投保的會議室、邀請、簽署欄位、錄影進度、遠距驗證狀態等執行期資料，均存於 Redis（TTL 約 24h）或 in-memory（ConcurrentHashMap）fallback。Redis Key 結構詳第十章。
現有儲存元件：MeetingRoomRepository（in-memory）、SigningStateRepository（Redis msp:signing:fields，in-memory fallback）、InMemoryInvitationRepository（Redis ekyc:invitation:token，fallback）、RecordingProgress（Redis ekyc:meeting:recording-progress）、remote-auth（Redis ekyc:meeting:remote-auth）。
5.2 共用平台層資料表（非遠投專屬）
下列為 common-service 既有平台表，遠距投保不直接擁有業務資料表，惟 API 稽核／錯誤紀錄可能涵蓋遠投呼叫。

第七章、通知作業
本功能之通知作業，係招攬員邀請要保人進行遠距投保時，由系統發送含遠距投保會議室連結與進入密碼之通知予要保人（未成年另含法定代理人），通知方式包含簡訊與電子郵件（詳見第三章 畫面一 招攬員邀請頁）。
會議室進入密碼由系統產生，客戶於客戶端登入頁輸入後由系統比對驗證；簡訊發送預計介接保誠 OTP 簡訊服務（sendOtpBySMS），實際端點待確認。除上述邀請通知外，本功能無其他系統主動推播（push）通知機制。

第十二章、FlowType 01~12 UI/UX 補充規格（v1.4 新增）
本章補齊遠距投保在不同 flowType、targetType、年齡與法定代理人情境下的 UI/UX 呈現規格。原則上，每一個需要客戶、法定代理人或招攬員操作的步驟，都必須清楚顯示目前操作者、下一位操作者、錄影狀態、生物辨識狀態，以及是否為同一場或 24H 內另一場會議。
11.1 設計總原則
• 任何畫面不得只顯示「客戶」二字；需依 flowType 顯示為「要保人本人」、「要保人法定代理人」、「被保人本人」或「被保人法定代理人」。
• 要保人與被保人不同人時，畫面需明確標示目前為 targetType=1 要保人端或 targetType=2 被保人端，且提示另一方需於 24H 內完成。
• 未滿 7 足歲情境由法定代理人代行操作，本人需與法定代理人同框入鏡；涉及 eKYC 時使用上下分割：上半框法定代理人、下半框本人。
• 7 至未滿 18 歲情境採法定代理人先操作、本人再操作；畫面需提供角色切換 Modal、目前角色標籤與下一位角色提示。
• 第二段錄影自確認告知事項開始，持續至招攬員與客戶雙方簽名完成；要保文件審閱階段不進行客戶生物辨識。
• 告知事項為前序已完成之健康告知問項再次核對，不是重新填寫。UI 文案應使用「核對」、「再次確認」、「資料是否正確」。
• 所有錄影失敗或返回 ePOS 調整情境，必須清楚告知會刪除或重錄的錄影段落，以及重新開始的步驟。

5. 要保人端完成頁：提示被保人端需於 24H 內完成，並顯示被保人端連結/通知狀態。
6. 被保人端入口：顯示目前處理 targetType=2，被保人端，第一位操作者為被保人法定代理人。
7. 被保人法代完成告知事項核對、簽署與投保內容聲明。
8. 跳出切換 Modal：請被保人本人入鏡。
9. 被保人本人完成告知事項核對、簽署與投保內容聲明。
10. 雙方完成頁：顯示要保人端、被保人端皆完成，系統回報 ePOS。
11.8 後續 mockup 製作命名規則
• 檔名格式：`flowType##_stage##_screenID_description.png`。
• 若畫面與 flowType 無關，使用 `common_stage##_screenID_description.png`。
• 同一畫面需同時產桌機招攬員端與手機客戶端時，分別加上 `_desktop_agent` 與 `_mobile_customer`。
• 畫面文字需使用實際角色名稱，不使用泛稱「客戶」；若姓名未知，使用「要保人本人」「被保人法定代理人」等角色稱呼。
